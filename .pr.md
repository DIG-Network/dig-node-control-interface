## What changed

The wallet-read freshness rule. A **`fallback`** answer is now bounded by the peak of the **tier that ANSWERED it** — the oracle's own reported height — with `synced` MEASURED against that peak, instead of being required to report `synced: false` / `peak_height: null` unconditionally.

The rule the crate published at 0.30.0, `src/results.rs:875`:

> A `fallback` answer MUST report `synced` `false` and `peak_height` `null` however caught-up the node's own replica is, because the oracle produced the figures and the replica neither produced them nor bounds their freshness.

and after:

> The bound MUST come from the party that PRODUCED the answer: a `fallback` answer MUST report the ORACLE's own peak as `peak_height` and `synced` MEASURED against that peak, and a `db` answer the replica's peak and `synced` measured against it. A node MUST NOT bound an answer by its own replica's peak, nor by the high-water mark of its held peers, when neither produced the answer — that stamps a freshness claim onto figures whose freshness it does not bound.
>
> `false` and `null` remain the honest answer in two cases, and a node MUST emit them there: an answering tier that tracks no peak of its own, and a CACHED row, which no live tier bounds.

This **refines** the old rule's stated reason rather than reversing it. The 0.30.0 objection was to a bound taken from a party that did not produce the answer; the new rule takes it from the party that did.

Files: `src/results.rs` (the normative paragraph plus the ten freshness field docs on the five tier-disclosing results), `SPEC.md` (the `coinById` freshness paragraph and the `WalletBalanceResult` tier paragraph), `src/kats.rs` (two new tests), `CHANGELOG.md`, `Cargo.toml`, `Cargo.lock`.

**Out of scope by construction:** `WalletPeakResult` and `WalletSyncStatusResult` carry no `source` field and are defined as the node's OWN replica height, so the answering-tier rule has nothing to bind there. Giving either a tier would be a wire-shape change and a separate decision.

## SemVer — minor, 0.30.0 → 0.31.0

Additive semantics on an existing `Option<u32>` per §5.1. **No wire-shape change:** the fields keep their types, and a fallback answer with `peak_height: null` remains legal (an answering tier that tracks no peak, and cached rows), so every existing golden KAT stays valid and passes unchanged. A 0.30.0 consumer that reads these fields keeps deserializing every payload losslessly; what changes is that a value it previously could never see is now reachable.

### The two tests, and the false green they are shaped against

The nearest wrong version of this change is the one this crate has already shipped once in the opposite direction: sweep `SPEC.md`, leave the field doc-comments alone. A test that searched only `SPEC.md` would pass on exactly that half-done change and the contract would be self-contradictory, with a reimplementer entitled to build against either half.

- `every_tier_disclosing_wallet_result_publishes_the_answering_tier_rule` walks the doc block above **each** `synced` / `peak_height` declaration inside every struct that declares `source: Option<WalletReadSource>`, and requires the rule marker there. It anchors on the `source` declaration rather than on an occurrence count, so a tier-disclosing result added later is covered the day it is added instead of silently lowering the denominator, and it asserts the count of fields it actually reached so a changed declaration shape fails loudly rather than measuring nothing.
- `the_superseded_unconditional_fallback_rule_is_stated_nowhere` bans the exact phrasings 0.30.0 published, across **both** files — adding the new sentence beside the old one is not an amendment.
